# HealthLens Development Instructions

This document provides a detailed overview of the HealthLens repository, its file structure, and actionable steps for further development, with a specific focus on completing the backend implementation.

## Repository Overview & Architecture

HealthLens is a remote patient-monitoring application divided into three main components (Interaction → Application → Intelligence):

1. **`frontend/` (Interaction)**: A React/Vite UI for both patients (logging vitals) and doctors (viewing rosters and alerts). Currently runs entirely on mock data to allow UI iteration.
2. **`backend/` (Application)**: A Node.js/Express API that serves the frontend, interacts with the Postgres database via Prisma, and publishes events to Kafka. *Currently a skeleton waiting for implementation.*
3. **`insight-worker/` (Intelligence)**: An independent Node.js daemon that consumes `vitals.logged` Kafka events, evaluates clinical rules, queries the Google Gemini API for pattern analysis, and generates AI-powered alerts and weekly summaries.

## File Structure

### Root Directory
- `docker-compose.yml`: Spins up the local infrastructure, primarily an Apache Kafka container (and optionally TimescaleDB/Postgres).
- `README.md`: High-level overview of the frontend and its purpose.

### `frontend/`
- **`src/types/index.ts`**: The single source of truth for the JSON data contract expected from the backend.
- **`src/services/`**: Network calls. Currently driven by `mockData.ts` based on the `VITE_USE_MOCKS=true` environment variable. When set to `false`, it uses `apiClient.ts` to call the real backend.
- **`src/pages/`**: Contains role-specific views (`patient/` and `doctor/`).
- **`src/components/`**: Reusable UI, Layout, and Chart components (using Recharts and Tailwind).

### `insight-worker/`
- **`src/ai/`**: Google Gemini API integrations and prompts for clinical analysis.
- **`src/rules/`**: Deterministic threshold and trend checking logic.
- **`src/schedulers/`**: Cron jobs (e.g., generating weekly summaries on Mondays).
- **`src/services/`**: Core logic for consuming Kafka events, writing alerts, and analyzing vitals.

### `backend/`
- **`src/server.ts`**: The entry point for the Express API.
- **`src/modules/`**: Domain-driven directories for `alerts`, `auth`, `patients`, `summaries`, and `vitals` (currently empty via `.gitkeep`).
- **`src/middleware/`**: For auth verification and error handling.
- **`src/kafka/`**: Intended for Kafka producer setup.
- **`src/db/`**: Intended for Prisma client instantiation.
- **`prisma/schema.prisma`**: The Postgres database schema, along with initial migrations.

## What Needs to be Done (Backend Development)

The backend is currently an empty Express shell serving only a root `/` endpoint. To connect the frontend to the real database and trigger the `insight-worker`, the following backend functionality must be implemented:

### 1. Database & ORM Setup
- Initialize the Prisma client inside `backend/src/db/index.ts`.
- Ensure the API connects smoothly using the models defined in `backend/prisma/schema.prisma`.

### 2. Kafka Producer Integration
- Set up a KafkaJS producer in `backend/src/kafka/`.
- When a patient submits a new vital reading (`POST /patients/:id/vitals`), the backend must save it to the DB and immediately publish a `vitals.logged` JSON event to the Kafka topic. The `insight-worker` relies entirely on this event to trigger rule evaluations.

### 3. Implement REST API Endpoints
You must implement the routes in `backend/src/modules/` to fulfill the frontend's API contract. Expected response shapes are strictly documented in `frontend/src/types/index.ts`.

**Auth (`/auth`)**
- `POST /auth/login`: Authenticate user (Patient/Doctor), issue a JWT bearer token.
- `POST /auth/logout`: Invalidate session.

**Patients (`/patients`)**
- `GET /patients/:id/dashboard`: Fetch today's metrics and a 7-day sparkline.
- `POST /patients/:id/vitals`: Save a `VitalsSubmission`, publish to Kafka, return `201 Created`.
- `GET /patients/:id/vitals`: Fetch historical vitals (filtering by range: 7d/30d/90d and type).
- `GET /patients/:id/vitals/log`: Paginated raw vitals log.
- `GET /patients/:id/profile`: Fetch patient profile data.
- `PATCH /patients/:id/profile`: Update profile data.

**Insights & Summaries**
- `GET /patients/:id/summaries`: Fetch Gemini-generated weekly summaries (generated by the insight-worker).
- `GET /patients/:id/alerts/history`: Fetch alert history for the patient.

**Doctor (`/doctor`)**
- `GET /doctor/overview`: Fetch stats, urgent alerts, and the doctor's patient roster.
- `GET /doctor/patients`: Fetch and filter the patient roster.
- `GET /doctor/patients/:id`: Fetch detailed patient view (profile, alerts, vitals log).
- `GET /doctor/patients/:id/thresholds`: Fetch custom alert thresholds.
- `PUT /doctor/patients/:id/thresholds`: Update thresholds.

**Alerts (`/alerts`)**
- `GET /alerts`: Fetch feed for the Alert Management Console.
- `PATCH /alerts/:id`: Update alert status and optional clinical notes.
- `POST /alerts/:id/follow-up`: Trigger a follow-up action/reminder for the patient.

### 4. Middleware Setup
- Implement a JWT-based authentication middleware in `backend/src/middleware/` to protect the routes. (Frontend expects a Bearer token in the `Authorization` header).
- Build a global error handler that catches exceptions and returns `{ "message": "error description" }` for all non-2xx responses.

### 5. Finalizing the Connection
Once the endpoints are implemented:
- In `frontend/.env`, set `VITE_USE_MOCKS=false` and configure `VITE_API_BASE_URL` to point to the backend server running on `http://localhost:3000`.
- Run `docker compose up -d` in the project root to spin up the required Kafka container.
- Spin up the `insight-worker` and `backend` using their respective commands.
